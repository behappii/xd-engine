# xd-engine

Софтверный (CPU) 3D-растеризатор на Rust, написанный с нуля. Ни OpenGL, ни
Vulkan, ни `glam` — вся математика, отсечение и растеризация свои, а видеокарта
занята единственным делом: показывает готовый массив пикселей на экране.

Проект учебный. Его смысл не в том, чтобы получить быстрый рендерер, а в том,
чтобы каждый шаг пути от вершины до пикселя был написан руками и понят.
Поэтому в коде много комментариев, и они объясняют не «что делает строка», а
почему сделано именно так и как здесь легко ошибиться.

## Запуск

Нужен Rust 1.85 или новее (проект на edition 2024).

```bash
git clone <url>
cd xd-engine
cargo run --release --example demo
```

`--release` здесь не формальность: без оптимизаций софтверный растеризатор
медленнее раз в десять. А `--example` — потому что крейт чисто библиотечный:
демо-сцена лежит в `examples/demo.rs` и подключает движок через тот же
публичный API, что и любой сторонний проект.

Демо-сцена ищет `textures/noname.png`. Каталог в репозитории пуст (картинки
не хранятся в git), поэтому без своего файла куб покажется с процедурной
шахматкой — в консоль при этом уйдёт предупреждение.

## Подключить в свой проект

Крейт не опубликован, поэтому зависимость по git или по пути — и **только
одна**:

```toml
[dependencies]
xd-engine = { git = "https://github.com/..." }
```

`winit` в свои зависимости добавлять **не нужно и не следует**. Движок
реэкспортирует его целиком (`xd_engine::winit`), плюс `xd_engine::KeyCode`
под рукой. Причина не в удобстве: `EventLoop` и `KeyCode` торчат наружу из
публичного API, и если игра объявит свой `winit`, а версия разойдётся с нашей
хотя бы в минорной цифре, в графе окажутся два разных `winit`. Его типы
перестанут совпадать с нашими, а ошибка будет выглядеть абсурдно — «expected
`KeyCode`, found `KeyCode`».

Дальше — как в `examples/minimal.rs` ниже, и `cargo run --release`.

**Про пути к картинкам.** `Texture::load("textures/wall.png")` отсчитывает
путь от рабочего каталога процесса. Пока запускаешь через `cargo run` из
корня проекта — совпадает, а вот у собранной игры, запущенной откуда угодно,
файл не найдётся. Для готовой сборки бери `Texture::decode(include_bytes!(...))`
и клади картинку прямо в бинарник, либо считай путь от `std::env::current_exe()`.

## Примеры

| Пример | Что показывает |
| --- | --- |
| `demo` | вся демо-сцена: текстуры, проволока, пол, деформация меша |
| `minimal` | минимум, с которого получается картинка |
| `scenes` | переключение сцен по `S` — две сцены на одних ресурсах |

```bash
cargo run --release --example minimal
cargo run --release --example scenes
```

Пример `scenes` показывает, ради чего ресурсы отделены от мира: меши и
текстура заводятся один раз, обе сцены ими пользуются, а переключение не
создаёт и не уничтожает ничего — сцены просто меняются местами через
`std::mem::swap`. Камера при этом часть сцены, поэтому переключение меняет
и точку обзора.

## Управление

| Клавиша | Действие |
| --- | --- |
| `W` `A` `S` `D` | движение камеры |
| `Space` / `Left Shift` | вверх / вниз |
| стрелки | поворот камеры |
| `Escape` | выход |

FPS выводится в заголовок окна. Окно можно тянуть за угол — буфер кадра
следует за размером, картинка не растягивается.

## Что уже работает

- **Своя математика:** `Vec2`, `Vec3`, `Vec4`, `Mat4`, модель–вид–проекция,
  перспективная матрица.
- **Растеризация по барицентрическим координатам** с перспективной коррекцией
  атрибутов: интерполируются `attr/w` и `1/w` по отдельности, а делятся уже
  в пикселе.
- **Depth-буфер по `1/w`.** Не по `z`: экранный `z` нелинеен, и
  барицентрически его интерполировать нельзя.
- **Освещение по Ламберту с затенением по Гуро.** Яркость считается в
  вершинах и размазывается по треугольнику.
- **Корректные нормали при неравномерном масштабе.** Нормали едут не по
  модельной матрице, а по обратной транспонированной (`Mat4::normal_matrix`,
  обращение — методом Гаусса–Жордана): иначе сплющенная фигура освещалась бы
  так, будто её грани повернулись в противоположную сторону.
- **Плоские и гладкие меши.** `flat_shaded` расщепляет вершины (у каждой
  грани своя нормаль), `smooth_shaded` их разделяет и усредняет нормали.
- **Текстуры:** UV задаётся по треугольникам, режим repeat (UV можно
  домножить и получить плитку). Тексель **умножается** на свет, а не заменяет
  его, поэтому Гуро виден и под текстурой.
- **Фильтрация двумя настройками:** отдельно для растянутой картинки
  (`Magnify`) и отдельно для сжатой (`Minify`), как в настоящих API. Разница
  не косметическая: только так получается «вблизи резкие квадраты, вдали
  никакой ряби» — то, что нужно пиксель-арту и полу, уходящему к горизонту.
  Мип-уровни выбираются по отпечатку пикселя в текселях, а строятся отдельным
  вызовом `with_mipmaps`: что лежит в памяти и как из неё читают — разные
  решения. Цена на 1600×1200 — 3.85 мс без фильтрации, 5.22 с билинейной,
  8.92 с мип-уровнями.
- **Готовые развёртки** у куба (грань = весь квадрат картинки) и у сферы
  (равнопромежуточная, с расщеплённым швом — чтобы `u = 0` и `u = 1` сошлись
  на одном меридиане, не оставив полосы в затенении).
- **Загрузка PNG и JPEG** из файла или из `include_bytes!`.
- **Отсечение задних граней** по знаковой площади в NDC и **клиппинг по
  ближней плоскости** алгоритмом Сазерленда–Ходжмана — с резкой не только
  позиций, но и атрибутов.
- **Проволочный режим** и покраска отдельных граней. Линии участвуют в
  depth-буфере наравне с заливкой: правильно прячутся за объектами и не
  затираются тем, что нарисовано после них.
- **Многопоточная растеризация** по горизонтальным полосам экрана: полосы не
  пересекаются, поэтому обходится без блокировок, а кадр побайтово тот же при
  любом числе потоков и любом расписании. Полосы разбирает постоянный пул
  `rayon` с work-stealing. На 11 ядрах, 1600×1200 — ×5.2 к однопоточному
  (16 → 3.1 мс, 60 → 328 FPS).
- **Меши и текстуры живут в `Assets`**, а инстансы держат `Copy`-хендлы:
  объявил меш один раз — переиспользуй сколько угодно, без `Rc` и `clone`.
  Ресурсы отделены от мира, поэтому сцен может быть сколько угодно, они делят
  одни арены и переключаются даром — а меню поверх игры это просто второй
  `draw` в тот же кадр.
- **Окно с изменяемым размером** и размен резкости на FPS через
  `RENDER_SCALE`.

## Как устроен кадр

```
Mesh (Vertex: позиция + нормаль + UV, локальные координаты)
  ↓ Instance::get_model_matrix       T · (Rx·Ry·Rz) · S
  ↓ Этап 1 — вершинный, инстансы параллельно, один проход по вершинам:
      позиция → MVP → clip space (Vec4)
      нормаль → normal_matrix → мир → яркость по Ламберту
      UV      → едет как есть
  ↓ is_backface — отсечение по знаковой площади в NDC
  ↓ ShadedVertex = clip-позиция + цвет + UV
  ↓ clip_triangle_near — Сазерленд–Ходжман по ближней плоскости
  ↓ плоский список треугольников — сцена дальше не видна
  ↓ Этап 2 — растеризация: кадр режется на горизонтальные полосы,
      полосы разбирает пул потоков rayon
  ↓ draw_triangle_filled — барицентрики с перспективной коррекцией
      цвет × Texture::sample(UV)
  ↓ DrawContext::set_pixel_depth — тест глубины по 1/w, запись в свою полосу
```

Модули:

| Модуль | Отвечает за |
| --- | --- |
| `math` | `Vec2` / `Vec3` / `Vec4` / `Mat4` — по файлу на тип |
| `scene` | `Assets`, `Mesh`, `Instance`, `Scene` и сборка кадра — по файлу на единицу |
| `renderer` | пиксели, растеризация треугольника, depth-тест — по файлу на единицу |
| `clipping` | отсечение по ближней плоскости |
| `texture` | загрузка картинки и выборка текселя |
| `app` | обработчик событий `winit`, главный цикл |
| `config` | константы: размер окна, свет, камера |
| `fps_counter` | счётчик кадров |

`src/lib.rs` — библиотечный крейт `xd_engine`, где живёт весь движок.
Исполняемой цели у крейта нет: демо-сцена — это `examples/demo.rs`, обычный
внешний потребитель. `Scene::draw` пишет в обычные срезы и окна не требует,
поэтому кадр рендерится прямо в тесте.

## Своя сцена

Этот код целиком лежит в `examples/minimal.rs` и запускается как
`cargo run --release --example minimal`. Он собирается при каждом
`cargo build --examples`, так что разойтись с настоящим API молча не сможет.

```rust
// winit берётся через реэкспорт движка, а не своей зависимостью:
// так его версия заведомо совпадает с той, на которой собран xd_engine
use xd_engine::{
    app::EngineApp,
    math::Vec3,
    scene::{Instance, Mesh},
    texture::Texture,
    winit::event_loop::EventLoop,
};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let event_loop = EventLoop::new()?;
    let mut app = EngineApp::new();

    // Меш и текстура отдаются сцене один раз. Обратно приходят хендлы —
    // обычные числа, Copy: раздавай их скольким угодно объектам
    let cube = app.assets.add_mesh(Mesh::create_cube());
    let checker = app.assets.add_texture(Texture::checker(
        64,
        8,
        [230, 230, 230, 255],
        [40, 40, 60, 255],
    ));

    // Цвет белый не случайно: тексель на него умножается, и любой другой
    // цвет сработал бы как светофильтр поверх картинки
    let mut textured = Instance::new(cube, Vec3::new(-1.2, 0.0, 0.0))
        .with_color([255, 255, 255, 255])
        .with_texture(checker);
    textured.scale = Vec3::new(0.6, 0.6, 0.6);
    app.scene.add_instance(textured);

    // Второй объект тем же мешем — просто ещё раз тот же cube
    let mut plain = Instance::new(cube, Vec3::new(1.2, 0.0, 0.0)).with_color([120, 190, 255, 255]);
    plain.scale = Vec3::new(0.6, 0.6, 0.6);
    app.scene.add_instance(plain);

    // Замыкание вызывается раз в кадр: сцена, зажатые клавиши, дельта времени
    let mut angle = 0.0f32;
    app.set_update(move |scene, _pressed_keys, dt| {
        angle += 45.0 * dt;

        for instance in &mut scene.instances {
            instance.rotation.y = angle;
        }
    });

    event_loop.run_app(&mut app)?;

    Ok(())
}
```

Для меша, который нужен ровно одному объекту, есть короткий путь:
`app.scene.spawn(Mesh::create_sphere(16, 24), position)` — он и регистрирует
меш, и заводит инстанс, возвращая `&mut Instance` для донастройки.

Готовые меши: `Mesh::create_cube()`, `Mesh::create_pyramid()`,
`Mesh::create_sphere(stacks, slices)`. Свою геометрию удобно собирать через
`Mesh::flat_shaded(&positions, &triangles)` или `Mesh::smooth_shaded(...)` —
обход треугольника **против часовой стрелки при взгляде снаружи**, иначе
отсечение задних граней съест грань.

## Текстуры

```rust
let photo = Texture::load("textures/wall.png")?;          // PNG или JPEG
let baked = Texture::decode(include_bytes!("../t.png"))?; // вшить в бинарник
let grid  = Texture::checker(64, 8, [230; 4], [40, 40, 60, 255]); // процедурная
```

Три вещи, о которые проще всего споткнуться:

- **Цвет инстанса не отменяется, а умножается** на тексель. Любой цвет кроме
  белого работает как светофильтр поверх картинки.
- **Плитка задаётся умножением UV**, а не режимом текстуры:
  `vertex.uv = vertex.uv * 12.0`. Работает потому, что выборка заворачивает
  координату дробной частью, отсчитанной вниз.
- **У меша должна быть развёртка.** У куба есть — каждая грань получает весь
  квадрат картинки; у сферы равнопромежуточная, как у обычной карты мира.
  У геометрии, собранной через `flat_shaded` без UV, развёртки нет, и
  текстура выродится в один тексель.

## Настройки

Всё в `src/config.rs`: стартовый размер окна, цвет фона, направление света и
фоновая подсветка, угол обзора, скорости камеры. Отдельно стоит
`RENDER_SCALE` — доля от физического размера окна, в которой считается кадр.
Цена кадра линейна по числу пикселей, так что `0.5` — это вчетверо меньше
работы и заметное «мыло»; растягиванием занимается GPU внутри `pixels`, и оно
бесплатно.

## Тесты

```bash
cargo test                     # всё: юнит-тесты + tests/render/
cargo test --lib               # только юнит-тесты внутри модулей
cargo test --test render       # только интеграционные
```

102 теста. Интеграционные видят движок только через публичный API и
рендерят настоящий кадр в буфер, а потом разглядывают пиксели. Ожидаемые
значения там по возможности считаются независимо от кода — формулой на
бумаге, а не повторением растеризатора: например, тест перспективной
коррекции подбирает геометрию так, что граница двух текселей обязана лечь на
столбец 82, а линейная интерполяция положила бы её на 50.

## Чего пока нет

- Анизотропной фильтрации: отпечаток пикселя берётся по большей стороне,
  поэтому пол под скользящим углом размывается сильнее, чем нужно.
- Смешивания: залитые пиксели всегда пишут альфу 255, альфа текстуры
  отбрасывается при загрузке.
- Отсечения по пирамиде видимости на уровне объекта.
- Чтения EXIF: фотография с телефона, снятая боком, ляжет на грань набок.

## Зависимости

Намеренно минимальные — всё, что относится к самому движку, написано руками:

| Крейт | Зачем |
| --- | --- |
| `winit` | окно и события ввода |
| `pixels` | вывод готового буфера пикселей на экран |
| `image` | декодирование PNG и JPEG (только эти две фичи) |
| `rayon` | пул потоков и work-stealing для растеризации |

Обе уступки сознательные. `image` — потому что внутри PNG поток, сжатый zlib
(Хаффман + LZ77), и свой распаковщик означал бы неделю работы над архиватором
вместо работы над графикой. `rayon` — потому что постоянному пулу нужно
одалживать буфер кадра, а у его потоков время жизни `'static`, и стыкуется
это только через стирание времени жизни в `unsafe`. Это единственное место в
проекте, где ошибка даёт не кривой пиксель, а неопределённое поведение, —
такой код правильнее взять обкатанный. Work-stealing достаётся сверху
бесплатно.
